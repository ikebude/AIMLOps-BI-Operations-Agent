## Held-out generalisation: left unchanged on purpose

The 11 misses (H09, H11-H13, H15, H18, H19, H21-H23, H25) are visible in `reports/eval_summary.json`. Any compiler change made after reading them would be fitted to the held-out set, and the score would stop meaning anything. The honest route is: write a new, frozen held-out set first (ideally by someone else), then improve the compiler using only in-sample phrasings and synonyms, and report old and new numbers on both sets. Not done here.

## Red team summary (guard)

60 inputs through `SQLGuard.validate` and, where accepted, executed via `BIOperationsEngine.ask`:
blocked: CTE/subquery/scalar-subquery/UNION reads of `sqlite_master`/`sqlite_schema`/`temp.sqlite_master`, quoted/bracket/backtick names, fullwidth/homoglyph/zero-width names, `pragma_*` TVFs, `PRAGMA`, `ATTACH`, `load_extension`, `readfile`, `edit`, `fts3_tokenizer`, `randomblob`, `zeroblob`, `json_each`, `dbstat`, comments, `;` chaining, `CREATE TEMP`, `INSERT ... SELECT`, `REPLACE`, `VACUUM INTO`, `RETURNING`, upsert, `LIMIT (subquery)`, 500-deep nesting.
accepted and bounded: cartesian triple join (interrupted at 5 s), unbounded `WITH RECURSIVE` (outer LIMIT), `LIMIT 0,100000` (rewritten to 2000), 3000-item `IN` list (124 ms), `printf` huge width (now NULL/too big).
API: no key 401, wrong key 401, 20,001-char question 422, whitespace 400; 800 fuzzed questions gave no 500s; max-length questions compile in < 35 ms.
